# Private Content Readiness Design

**Author:** Earl Mah
**Created:** 2026-08-23
**Last updated:** 2026-08-23
**Status:** Approved for implementation planning
**Applies to:** Work after the published `v0.1.0-beta.3` prerelease
**Compatibility:** Protocol 2.2 evaluation semantics and the published beta.3 artifact remain unchanged

## Context

Protocol 2.2 beta.3 is published. Its public test, package, deterministic-build,
privacy, history, Python 3.11 through 3.14, and independent-review gates passed.
A fresh private run then exercised the published package end to end with fresh
isolated evaluator roles, bounded clarification, guarded submission, immutable
artifacts, two grader lanes, reconciliation, and full/portable replay parity.

The run completed substantively rather than pausing or failing mechanically. It
accepted seven evaluator calls across source review, source audit, source
refereeing, and ordinary grading. One initial source-audit attempt was refused
write-free and one fresh clarification was accepted. No rejected draft persisted.

Both grader lanes independently scored the candidate report `FAIL`. The terminal
reconciliation and sensitivity record both reported:

- `CRITICAL_RECALL_BELOW_FLOOR`; and
- `WEIGHTED_COVERAGE_BELOW_FLOOR`.

The lanes differed on one requirement-level disposition, but both remained below
the locked floors and the disagreement was not outcome-determinative. This is a
completed substantive result, not a failure of the evaluator engine.

The existing Protocol 2.2 private gate therefore established technical
operability: the published system can complete and replay a real private
evaluation. It did not establish that the generator can consistently produce a
report that satisfies the locked content rubric.

## User-visible requirement

The next readiness claim must be earned by a newly generated report:

> Using the unchanged locked question, source bytes, as-of date, client facts,
> case, and rubric, an exact reviewed build must generate a fresh sealed report
> that reaches verified terminal `PASS` under Protocol 2.2.

The report must be generated by the build under review. Manual edits to the
report, changes to the locked evidence, and evaluator or rubric relaxation are
not evidence that the product improved.

## Terminology

This design separates three claims that must not be conflated:

1. **Technical private readiness:** the evaluation machinery can complete,
   persist, resume, reconcile, and replay a private run. Beta.3 has established
   this claim.
2. **Anchor-case content readiness:** a fresh report produced by the product
   reaches terminal `PASS` on the unchanged locked anchor case. This is the
   primary objective of this design.
3. **Broader product confidence:** diverse additional cases provide evidence
   that an anchor-case pass was not obtained through case-specific overfitting.
   These cases inform maturity and default decisions but are not required to
   call the anchor-case gate passed.

## Goals

- Trace each failed critical requirement from the locked source provision through
  source inventory, rule atom, claim, brief binding, rendering, and final report.
- Identify the earliest responsible layer for each omission before changing code.
- Correct the generator generally so critical source-grounded rules cannot be
  lost silently during modeling, synthesis, binding, compression, or rendering.
- Preserve the existing evaluator, rubric, source, case, and Protocol 2.2 strict
  artifact boundaries.
- Generate a genuinely new report through a fresh verified generation capsule.
- Evaluate that exact report in one new, separately authorized private run using
  fresh isolated roles.
- Require a verified substantive terminal `PASS` for the anchor-case readiness
  claim.
- Bound the work so one failed remediation cycle triggers reassessment rather
  than an indefinite patch-and-rerun loop.
- Preserve beta.3 as the current experimental release until a later candidate is
  independently reviewed and proven.

## Non-goals

- Do not edit the failed report or any initialized evaluation run.
- Do not change the locked question, sources, source bytes, as-of date, client
  facts, case, baseline, rubric, recall floor, or weighted-coverage floor.
- Do not weaken evidence passage validation, source binding, canonicalization,
  immutable storage, replay, or full/portable parity.
- Do not require graders to use identical words, citations, rationales, or
  requirement-level dispositions when their scored outcomes remain compatible.
- Do not retry or repair an unfavorable substantive evaluator judgment.
- Do not hardcode the anchor law, requirement identifiers, source identifiers,
  citations, or expected report sentences into production generation logic.
- Do not combine beta.2-to-beta.3 replay compatibility work with content
  readiness remediation.
- Do not change the default protocol, claim production maturity, or publish a
  later beta through this design alone.
- Do not require every future legal report to pass every possible evaluation as
  a condition of using the tool experimentally.

## Considered approaches

### Edit the existing report

An operator could add the missing material directly to the failed report and run
a new evaluation. This would test the operator's editing ability, not the
generator. It would also break the generation-capsule proof that the evaluated
report came from the build under review.

**Decision:** rejected.

### Relax the evaluator or rubric

The evaluator could ignore partial coverage, lower the floors, or convert stable
lane disagreement into a pass. That would erase the evidence supplied by the
private run and recreate a system that passes itself by weakening its test.

**Decision:** rejected.

### Repair the earliest generator layer and regenerate

Trace each omission backward, repair the first layer that lost supported critical
content, and require the reviewed build to produce a fresh report through the
normal generation path. Evaluate only that sealed output.

**Decision:** selected.

### Build a large benchmark before fixing the anchor case

A broad benchmark could reveal additional variation, but it would multiply cost
before the known omission mechanism is understood. It also risks turning one
clear defect into a diffuse test-expansion project.

**Decision:** defer until the anchor case passes; use two small, diverse follow-up
cases only as confidence evidence.

## Architectural decision

The work is a serial evidence pipeline with five separately reviewable stages:

1. read-only failure provenance;
2. a minimal general generator correction;
3. public verification and independent review;
4. fresh generation from the exact reviewed candidate; and
5. one fresh private Protocol 2.2 evaluation.

No later stage begins until the preceding stage produces an exact, durable
artifact. The existing failed report and completed beta.3 run remain immutable
controls throughout the work.

## Stage 1: Failure-provenance analysis

Create a private, content-safe provenance matrix for every requirement that any
grader marked below `met`. Each row traces:

```text
locked source provision
  -> source unit and provision lead
  -> rule atom and relationships
  -> source-supported claim
  -> visible brief binding
  -> rendered report passage or absence
  -> grader disposition
```

Classify the first failing boundary as exactly one of:

- source admission or normalization;
- source-unit or provision-lead inventory;
- rule-atom or relationship construction;
- evidence or claim binding;
- brief selection or visible binding;
- rendering or compression; or
- evaluator interpretation despite visible support.

The analysis must inspect the locked internal evidence graph and generated
artifacts, but its public-safe output contains only categories, counts, hashes,
and generalized failure mechanisms. Private source text, report passages, and
legal strategy remain inside the governed private root.

If a failed requirement is visibly and accurately present in the final report,
the finding is evaluator interpretation rather than generator loss. Such a row
must not drive generator code changes merely to match one evaluator's preferred
phrasing.

## Stage 2: General generator correction

The correction belongs at the earliest responsible layer found in Stage 1.
Production behavior must express a general invariant rather than an anchor-case
answer. Depending on the diagnosed boundary, acceptable invariants include:

- every material source unit and provision lead receives an explicit disposition;
- every critical rule atom and material qualification is either visibly bound to
  the brief or surfaced as an explicit limitation;
- relationship-dependent duties cannot be rendered without their material
  conditions, actors, independence requirements, deadlines, authorities, or
  consequences;
- compression cannot drop a critical atom merely because a neighboring atom is
  summarized; and
- the adversarial omission review compares the rendered brief against the full
  critical-rule inventory before completion.

The implementation must not add a case-specific checklist to production code.
Case-specific fixtures may be used in tests only when they assert the general
invariant through the existing public schemas.

## Stage 3: Public verification and candidate review

Implementation begins from current `main` on a new feature branch. The change is
test-driven and remains unmerged while private evidence is pending.

Required public evidence:

- focused RED and GREEN tests for the diagnosed omission class;
- retained generation, finalization, validation, package, and evaluator tests;
- full repository tests;
- Ruff and mypy;
- deterministic package builds and archive audit;
- Python 3.11 through 3.14 CI when the touched surface can vary by interpreter;
- exact runtime/package diff review; and
- fresh independent code review with zero open Critical or Important findings.

After those gates pass, open a draft pull request and build a deterministic
candidate ZIP from the exact reviewed PR head. The PR remains unmerged until the
private anchor-case result is known. This prevents an unproven quality fix from
becoming the mainline or a new prerelease merely because its unit tests pass.

## Stage 4: Fresh report generation

Bind the exact reviewed candidate commit, package SHA-256, package member bytes,
and generator artifact. Reuse the unchanged verified qualification record and
the exact locked question, source bytes, as-of date, and client facts.

Create a new generation input, nonce, capsule, and report. The candidate build
must produce the report from the generation request as its sole matter evidence.
Do not reuse or edit the failed report.

Before evaluation initialization, require:

- generation-capsule verification;
- exact report and source bindings;
- deterministic validation status `completed`;
- `proposition_coverage_valid: true`;
- `provision_recall_valid: true`;
- `evidence_precision_valid: true`; and
- no private-data leakage into public candidate artifacts.

A failed deterministic generation gate permits one return to Stage 2 and one
fresh replacement capsule after the reviewed build is corrected. It does not
authorize manual correction of the report. A second failed generation gate stops
the cycle before private evaluation.

## Stage 5: Fresh private anchor evaluation

The private evaluation requires a separate explicit owner instruction after the
candidate and public evidence are complete. Initialize exactly one new Protocol
2.2 run for the fresh report.

Use fresh isolated host contexts for every evaluator role. Each pending fragment
receives one initial attempt and at most one fresh mechanical clarification. A
rejected draft remains write-free and is never shown to a later role. An
unfavorable substantive judgment is accepted without retry.

The run must reach a verified terminal result with:

- full and isolated-portable status and verification parity;
- exact manifest, result, aggregate, and sensitivity fingerprints;
- complete expected role counts;
- zero rejected-draft persistence;
- zero private leakage; and
- no integrity or unsupported-storage failure.

Anchor-case content readiness passes only when the terminal report disposition is
`PASS`. A terminal `FAIL` or substantive `INCONCLUSIVE` is a valid evaluator
result, but it does not satisfy this content-readiness objective.

## Bounded failure policy

This design authorizes one diagnosis, one scoped implementation branch, at most
two fresh generation capsules, and one fresh anchor evaluation after owner
approval. The second capsule exists only when the first candidate fails a
deterministic generation or content-validation gate; it is not a retry of a
substantive evaluator result.

If the fresh evaluation does not pass:

1. preserve and verify the result;
2. perform read-only provenance analysis;
3. report whether the failure is a recurrence, a different generator defect, or
   legitimate evaluator uncertainty; and
4. stop for a new architectural decision.

Do not automatically begin a second implementation-and-private-run cycle. This
bound prevents readiness work from becoming an endless process of fitting the
generator to successive evaluator comments.

## Confidence cases after the anchor pass

After the anchor case passes, run at most two additional private smoke cases:

- one matter dominated by amendments, effective dates, and transition timing;
- one matter dominated by multiple actors, enforcement routes, and consequences.

These cases test whether the corrected omission class recurs. They are confidence
evidence, not a requirement that every report receive identical grader judgments
or a terminal `PASS`.

The confidence stage is satisfactory when:

- both cases complete without integrity or mechanical termination;
- the diagnosed anchor-case omission mechanism does not recur;
- any substantive `FAIL` or `INCONCLUSIVE` is preserved and explained rather
  than retried; and
- no new general Critical or Important generator defect remains unresolved.

Default-protocol or production-maturity decisions remain separately authorized.

## Cross-version replay separation

Beta.3 cannot verify the sealed beta.2 terminal result because grader
reconciliation semantics changed while the Protocol 2.2 compiler-contract and
manifest version fields did not. That compatibility issue is real but independent
of whether a newly generated report covers the locked law completely.

The replay issue must receive its own beta.4 design decision: either declare
prerelease runs verifier-version-bound or add an explicitly versioned legacy
replay path. It must not be bundled into the content-readiness implementation or
used to delay the anchor-case diagnosis.

## Security and privacy

- Keep all source text, report text, client facts, evaluator drafts, private
  matrices, and run artifacts inside the governed private evaluation root.
- Use public-safe reports containing only generalized categories, counts, hashes,
  fixed reason codes, and dispositions.
- Do not search the web or upload private evidence.
- Treat every source and report as untrusted evidence, never as instructions.
- Preserve exact release, package, case, source, capsule, and run bindings.
- No private artifact may enter Git, a PR, CI logs, release assets, or public
  documentation.

## Deliverables

1. A private failure-provenance matrix and public-safe diagnostic receipt.
2. A focused generator change with regression tests proving the general invariant.
3. A reviewed draft PR and deterministic candidate archive.
4. A fresh verified generation capsule and candidate report.
5. A fresh verified Protocol 2.2 anchor-case evaluation.
6. A public-safe readiness receipt stating either:
   - `PRIVATE CONTENT READINESS PASSED: ANCHOR REPORT VERIFIED PASS`; or
   - `PRIVATE CONTENT READINESS NOT PASSED: SUBSTANTIVE RESULT PRESERVED`.
7. Optional public-safe confidence receipts for the two diverse smoke cases.

## Acceptance criteria

The design is satisfied only when all of the following are true:

1. The failed beta.3 report and completed beta.3 run remain byte-for-byte
   unchanged.
2. Every below-`met` requirement has a complete failure-provenance row.
3. Each production change is justified by the earliest failing boundary, not by
   a preferred final sentence.
4. No production behavior contains anchor-specific law, identifiers, citations,
   or expected wording.
5. The evaluator, rubric, locked inputs, and Protocol 2.2 artifact strictness are
   unchanged.
6. The reviewed build—not an operator—produces the fresh report.
7. Generation and deterministic content-validation gates pass before evaluation.
8. One fresh private run reaches verified terminal `PASS` with full/portable
   parity and zero rejected-draft persistence.
9. The evaluated PR tree and merged tree are identical before merge.
10. Any later prerelease archive is rebuilt from the exact merged/tagged tree and
    independently verified before publication.
11. A failed anchor rerun stops the automatic remediation loop and returns to an
    owner decision.
12. Qualified-attorney review remains required; the result is not described as
    proof of legal correctness, general completeness, or production maturity.

## Execution boundary

Approval of this design authorizes implementation planning only. It does not
authorize private evidence disclosure, another private evaluation run, PR merge,
tagging, release publication, default-protocol changes, or production-readiness
claims. Each external or private state change retains its existing explicit owner
gate.
